## 第一章 软件简介

### 1.1 产品概述

HodoopForge 是一款企业级Hadoop集群部署与管理平台软件，专为解决 Apache Ambari 3.x 与 Apache Bigtop 3.5.0及以上版本之间联调困难、兼容性差、部署复杂等问题而开发。

该软件在深度优化 Apache Ambari 的基础上，完美集成并增强了 Bigtop 的打包与组件管理能力，对相关 Stack、服务定义、元数据、部署脚本等进行了专项定制与重构，填补了当前开源生态中这一关键空白。

#### 1.1.1 产品定位

HodoopForge 定位为企业级大数据平台部署工具，主要解决以下问题：

1. **版本不匹配问题**：Apache Ambari 3.1.0 默认支持 Bigtop 3.2.x，而 Bigtop 3.5.0 已发布，两者存在版本差距，导致无法直接使用新版本组件。

2. **部署复杂问题**：传统Hadoop集群部署需要准备多台物理机或虚拟机，配置复杂，资源消耗大，部署时间长，通常需要数天时间完成。

3. **兼容性问题**：新版本组件（如Hive 4.0.1）与Ambari存在兼容性问题，包括配置格式差异、API变化、认证方式调整等。

4. **缺乏集成方案**：市面上没有成熟的Ambari 3.x + Bigtop 3.5.x集成方案，企业用户难以快速部署生产级大数据平台。

#### 1.1.2 核心价值

| 价值点 | 描述 |
|-------|------|
| 快速部署 | 4节点集群部署时间从数天缩短至小时级别，大幅降低部署成本 |
| 无缝集成 | 实现Ambari 3.1.0与Bigtop 3.5.0的深度集成，提供统一的部署入口 |
| 自动修复 | 内置兼容性修复脚本，自动检测并解决已知问题，减少人工干预 |
| 离线支持 | 本地RPM包管理，无需互联网连接即可完成部署，适合内网环境 |
| 生产可用 | 经过实际测试验证，支持企业级生产环境部署，稳定可靠 |

#### 1.1.3 产品特色

**特色一：首创性解决方案**

HodoopForge 是目前市面上首个彻底打通 Ambari 3.1.x 与 Bigtop 3.5.x 的集成平台。通过以下技术手段实现了两者的无缝集成：

- **动态继承机制**：自动检测现有Stack版本，继承并扩展至3.5.0
- **元数据自动更新**：批量更新所有服务的组件版本号
- **包路径修复**：修正bigtop-select的命令路径映射
- **VDF自动生成**：根据组件清单自动生成版本定义文件

**特色二：容器化快速部署**

基于Docker Compose的多节点集群定义，使用 bigtop/puppet 官方镜像作为基础环境，用户可在单台服务器上快速搭建4节点Hadoop集群。容器化部署具有以下优势：

- **环境隔离**：每个节点运行在独立容器中，互不干扰
- **快速重建**：可以快速销毁和重建集群，便于测试和开发
- **资源控制**：通过Docker资源限制功能控制各节点资源使用
- **端口映射**：通过端口映射实现从宿主机访问集群服务

**特色三：智能兼容性修复**

内置多项兼容性修复脚本，自动检测并修复Hive 4.0.1等组件与Ambari的兼容性问题，包括：

- hive.exec.post.hooks 配置修复：将空格值改为空字符串
- service_advisor.py bug修复：修正返回值格式
- hive_check.py 认证参数修复：将auth=noSasl改为auth=none
- HDFS目录权限修复：设置正确的目录所有者和权限
- Metastore schema初始化：自动创建数据库表结构

HodoopForge 适合用于大数据技术教学培训：

- **快速重建**：学员可以随时重建集群，进行各种实验
- **低成本**：单台服务器即可搭建完整集群，降低培训成本

#### 1.5.3 生产环境预研

HodoopForge 可用于生产环境的预研和验证：

- **架构验证**：验证技术架构的可行性

## 第七章 常见问题

### 7.1 安装问题

#### Q1：容器启动失败

**问题描述**：执行`docker compose up -d`后容器未正常启动。

**专项注意**：`docker compose up -d` 在容器配置、镜像或网络与 compose 定义不一致时会执行**重建（先删后建）**，导致容器内已装软件（Ambari/Hadoop/MySQL）**全部丢失**；日常重启请使用 `docker compose restart`（保留数据层）。曾出现过清理网段冲突执行 `docker network rm` 后 `up -d` 误触发重建的情况，详见本节"容器重建后全量丢失"。

**排查步骤**：

1. 检查Docker服务状态
2. 检查Docker版本兼容性
3. 查看容器日志
4. 检查磁盘空间

**解决方案**：

```bash
# 检查Docker服务
systemctl status docker

# 检查Docker版本
docker --version

# 查看容器日志
docker compose logs

# 检查磁盘空间
df -h /var/lib/docker
```

#### Q2：SSH免密登录失败

**问题描述**：节点间SSH连接需要密码。

**解决方案**：

```bash
# 重新执行setup.sh脚本
./setup.sh

# 检查authorized_keys文件权限
docker exec bigtop_hostname0 ls -la /root/.ssh/authorized_keys
# 应显示: -rw------- (600)

# 检查sshd服务状态
docker exec bigtop_hostname0 systemctl status sshd
```

#### Q3：仓库访问失败

**问题描述**：无法访问http://bigtop_hostname0。

**解决方案**：

```bash
# 检查Nginx服务状态

# 检查防火墙设置
docker exec bigtop_hostname0 firewall-cmd --list-all

# 检查/etc/hosts配置
docker exec bigtop_hostname0 cat /etc/hosts
```

#### Q3-1：容器被"重建"而非"重启"导致集群全部丢失

**问题描述**：执行`docker compose up -d`后，Ambari UI 无法访问，容器内 `/usr/lib/ambari-server`、`/var/lib/mysql` 均不存在，`setup-hostname.sh` 报"栈目录/包不存在"。

**问题原因**：容器被 **Recreate（重建）** 而非 Restart（重启）。重建会把容器**先删后建**，可写层清零——已安装的 Ambari、Hadoop、MySQL 及其数据全部消失，bind mount 卷（RPM 仓库、/etc/hosts）仍在。典型诱因：清理与 compose 网段冲突的旧网络时执行过 `docker network rm <网络名>`，随后 `up -d` 判定容器配置不一致而重建。

**判定方法**：

```bash
docker compose ps   # 重建时 Created 时间会变成最近一次 up -d 的时刻
docker compose exec bigtop_hostname0 bash -c \
  'test -d /usr/lib/ambari-server && echo KEEP=重启 || echo WIPED=重建'
# 输出 WIPED=重建 即为容器被清空
```

**解决方案（全量重装，无法通过重启恢复）**：

```bash
cd ambari3
docker compose up -d
cd scripts
./setup.sh                # 步骤一：初始化节点
./setup-ambari-repo.sh    # 步骤二：构建本地YUM仓库
cd ..
./scripts/install-ambari-server.sh   # 步骤三：安装Ambari Server
./scripts/install-ambari-agent.sh    # 步骤四：安装Ambari Agent
# 步骤五：Web界面创建集群（http://localhost:20609，见第四章 4.2）
# 步骤六：Deploy失败时执行修复脚本后重试，直至成功：
./scripts/post-deploy-fixes.sh
# 步骤七：启动全部服务后执行 Hive 修复：
./scripts/fix-hive.sh
```

**规避原则**：清理冲突网络前先 `docker compose down`；拿不准时用 `docker compose restart`（保层）而非 `up -d`。

#### Q3-2：部署脚本报"反斜杠续行内夹注释"语法错误

**问题描述**：执行 `setup.sh` 报 `未预期的符号 '||' 附近有语法错误`，或 `install-ambari-server.sh` 在中途报 `sed: no input files` 后停止（Ambari Server 未启动）。

**问题原因**：shell 脚本中 `\` 反斜杠续行后紧跟 `# 注释` 行会**打断续行**，注释后的内容被当成新命令执行，在 `set -e` 下直接导致脚本失败。该问题已在 `setup.sh`、`install-ambari-server-script.sh` 中修复（注释一律移到续行块之前或之后）。

**排查命令**（找出所有"上一行以\结尾、本行是注释"的可疑位置）：

```bash
awk 'prev ~ /\\$/{ c=$0; gsub(/^[ \t]+/,"",c); if (c ~ /^#/) print FILENAME": line "FNR } { prev=$0 }' scripts/*.sh
```

### H.4 容器被重建导致集群全量丢失（真实案例）

**问题描述**：
为清理与 compose 网段（172.19.0.0/24）重叠的残留网络，执行了 `docker network rm ambari3_default`（占 172.19.0.0/16），随后 `docker compose up -d`。结果 4 节点容器 `Created` 时间变为同一时刻、`/usr/lib/ambari-server` 与 `/var/lib/mysql` 全部消失、`rpm -qa | grep -i ambari` 无输出。此前认为只是"重启"即可恢复，经取证确认 **Recreate 已把容器可写层清零**，无法通过重启或修复脚本恢复。

**排查步骤**：

```bash
docker compose ps          # Step 1：Created 时间被刷新 → 已重建
docker compose exec bigtop_hostname0 bash -c \
  'test -d /usr/lib/ambari-server && echo KEEP || echo WIPED'
docker compose exec bigtop_hostname0 rpm -qa | grep -i ambari   # 无输出 → 软件已丢
```

**解决方案（全量重装）**：

```bash
cd ambari3
docker compose up -d
cd scripts
./setup.sh
./setup-ambari-repo.sh
cd ..
./scripts/install-ambari-server.sh
./scripts/install-ambari-agent.sh
# Web 界面创建集群（http://localhost:20609，BIGTOP 3.5.0、4 个 FQDN、仓库 Bigtop-3.5.0.0-1）
# Deploy 失败 → ./scripts/post-deploy-fixes.sh → Retry，循环至全部成功
# 启动全部服务后 → ./scripts/fix-hive.sh
```

**经验教训**：

1. `docker compose up -d` 与 `docker compose restart` 行为不同：前者在配置/网络不一致时执行 Recreate（丢层），后者保留可写层。
2. 清理冲突网络务必先 `docker compose down`，再 `docker network rm`。
3. 挂载卷（RPM 仓库、hosts）会保留，不要因"卷还在"误判软件仍在。
4. 判定"重启态/重建态"是恢复的第一步，见第七章 Q3-1。
